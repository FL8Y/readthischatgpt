# Addendum: how content is structured and authored (AnkiDroid 2.25.1)
Method: strings over `ex/lib/arm64-v8a/librsdroid.so` (Rust, stripped; English Fluent `.ftl` text embedded; line refs are in `strings` output), plus `ex/assets/*`, manifest. No code executed. All content treated as data.
Labels: **OBSERVED** = literal string/file seen. **INFERRED** = upstream-Anki knowledge or adjacency, not seen verbatim. **COMMUNITY** = convention, not in files.
Caveat: the stock note-type templates are stored in the .so as fragmented/interned pieces (e.g. `{{type:}}`, `{{#}}<div>{{}}</div>{{/}}`), where the field name is spliced in at runtime from the localized field-name strings. So full qfmt/afmt are reconstructed (INFERRED), pieces are OBSERVED.

## 1. Data model (INFERRED from upstream + OBSERVED fragments)
- Collection > Decks > Cards; Notes belong to a Note Type (notetype); a note holds N ordered **fields** (stored joined in `n.flds`, OBSERVED in SQL fragments `n.flds like`, `regexp_fields(?, n.flds,`), plus `n.tags`, `n.mid` (notetype id), `c.ord` (template index), `c.did` (deck), `c.odid` (original deck when in filtered deck).
- A note type = fields + card templates (each with qfmt/afmt) + one shared CSS + LaTeX header/footer (`\documentclass[12pt]{article}`, `\usepackage{amssymb,amsmath}`, `\pagestyle{empty}` OBSERVED) + kind (normal | cloze).
- OBSERVED search fragments showing the addressable structure: `n.mid in (select id from notetypes where name = ?)`, `(n.mid,c.ord) in (select ntid,ord from templates where name = ?)`, `c.did in (...)`, `regexp_tags(?, n.tags)`, `n.tags = ''`, `(c.flags & 7) ==`.

## 4. Cloze syntax and card generation
- OBSERVED regex: `(?s)\{\{c[\d,]+::(.*?)(::.*?)?\}\}` => `{{c1::text}}`, `{{c1::text::hint}}`, and multiple numbers `{{c1,2::text}}` (the `[\d,]+`). Sample OBSERVED: `This is a {{c1::sample}} cloze deletion.`
- Cloze card count = number of distinct c-numbers in the Text field (INFERRED; consistent with `Cloze { $val }` template naming and `card_ords_duplicated`/`template_idx` fields). Empty-card cleanup OBSERVED: `Delete Empty Cards`, `Delete Empty Notes`, "No empty cards."
- Normal types: one card per template whose front renders non-empty (INFERRED rule; OBSERVED supports: `CardRequirement`, `field_ords`, `partial_render`, `fill_empty`, error "front of card is blank", "This will create N cards. Proceed?" when editing templates). "Optional reverse" works through `{{#Add Reverse}}` conditional on the front.
- Duplicate check: first field of the note type (OBSERVED strings: "Duplicate with first field", "Update existing notes when first field matches", `Match scope`: notetype / notetype and deck).

## 8. Multiple-choice questions (COMMUNITY, not present in the app files)
- Not a built-in note type: only one stray string `Multiple Choices` (OBSERVED, line ~226, an orphan in a binary blob; no template/feature behind it).
- COMMUNITY convention: a custom note type with fields e.g. `Question`, `Options` (or `A`..`E`), `Answer`/`Correct`, `Explanation`. Front template renders question + options (often lists via `<ol>`; an inline `<script>` shuffles them using `Math.random`, stores selection, and compares with `{{Answer}}`); back template uses `{{FrontSide}}<hr id=answer>` then highlights correct/incorrect and shows `{{Explanation}}` (via `{{#Explanation}}...{{/Explanation}}`). Alternative no-JS approach: cloze with `{{c1::answer}}` and a separate options field or `{{type:Answer}}`, or one card per option via conditionals. Data stored in fields only, so import/export via CSV works. AnkiDroid exposes `ankiAnswerEase1-4`, `ankiShowAnswer`, `ankiGetCardId` etc. so JS in the template could auto-answer (see 9).
- Caution: such JS runs in the app WebView; fields are rendered as trusted HTML in the card (notes from shared decks can contain scripts). Backend has `ammonia` HTML sanitizer for some paths (OBSERVED crate), but template JS itself is not sanitized (INFERRED).
